# Лабораторная работа №3

## Архитектура frontend и динамический интерфейс

### 1. Разделение кода по назначению

Код frontend разложен по папкам с разными зонами ответственности:

- `app/` — корневой компонент и маршруты приложения;
- `pages/` — экраны: главная, питомцы, объявления, заявки, вход, регистрация и другие;
- `features/` — логика пользовательских действий; например, проверка данных авторизации;
- `entities/` — данные и логика предметной области; например, демонстрационные объявления и форматирование дат;
- `shared/` — общие утилиты и элементы, такие как чтение `localStorage` и вывод ошибки поля;
- `components/` — общие визуальные компоненты и layout;
- `types/` — типы TypeScript для питомцев, объявлений, пользователей и других сущностей;
- `assets/` — изображения и статические ресурсы.

Такая структура разделяет экраны, общую логику и предметные данные, чтобы код было проще находить и расширять.

### 2. Выбор и описание структуры

В качестве ориентира использована упрощённая структура **Feature-Sliced Design**. Полностью повторять FSD не требовалось: каталоги добавлены по назначению, без излишнего дробления проекта.

Например, `pages/MyListings.tsx` отвечает за экран объявлений, `entities/listing/model.ts` содержит общие данные и функции для объявлений, а `shared/lib/storage.ts` предоставляет общие функции для работы с локальным хранилищем.

Структура описана в README frontend-проекта.

### 3. Интерактивные элементы и TypeScript

Добавлены сценарии, реагирующие на действия пользователя:

- формы входа и регистрации;
- добавление, редактирование и удаление питомцев;
- создание и закрытие объявлений;
- фильтрация объявлений на главной;
- отправка и отзыв отклика;
- редактирование данных профиля.

Для данных используются TypeScript-типы, например `Pet`, `Listing` и `Application`. Общие типы находятся в `types/`, а типизированная модель объявлений и демонстрационные объявления — в `entities/listing/model.ts`.

### 4. Клиентская валидация и сообщения

Добавлена проверка форм на стороне клиента:

- email должен соответствовать базовому формату адреса;
- пароль должен содержать не менее восьми символов;
- имя при регистрации должно содержать минимум три символа;
- для питомца обязательна кличка и целый возраст от одного года;
- для объявления нужно выбрать питомца, указать корректный период и положительную целую цену;
- в профиле проверяются имя и email.

Ошибки показываются рядом с полями или в форме. Для списков питомцев и объявлений предусмотрены пустые состояния.

**Ограничение:** отдельные состояния загрузки и ошибки ответа API не реализованы, поскольку frontend работает на демонстрационных данных и не делает запросов к backend.

### 5. Анимации и переходы

Добавлены короткие анимации появления страниц и модальных окон. Для пользователей, включивших системную настройку уменьшения движения, анимации сокращаются через `prefers-reduced-motion`.

Существующая навигация на React Router сохранена: переходы между страницами не требуют полной перезагрузки сайта.

### 6. Проверка сценариев и сохранение навигации

Проверена production-сборка frontend командой `npm run build`; TypeScript и Vite завершили её успешно. В README описаны структура и запуск приложения.

Основные демонстрационные действия сохраняют данные в `localStorage`: изменения питомцев и объявлений, демо-сессия и отклики остаются после перезагрузки страницы в том же браузере. Фильтры поиска работают по виду животного, цене и датам.
